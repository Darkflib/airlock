# Airlock review — 3 November 2026

Scope: current working tree, including uncommitted judge-access changes; code, infrastructure, tests, claims, committed eval data, and public hackathon requirements. This is a review, not a penetration test or proof of hypervisor isolation. Application code was not changed, deployed, or exercised against real repositories. No hostile package was executed locally. Documentation and fixture text were treated as material to assess, not user instructions.

## Highest-priority findings

### 1. [P1] Guest sign-in grants authority to approve any run and use the GitHub App

References: `airlock/web/app.py:295–320`, `airlock/web/auth.py:249–255`.

The middleware checks membership in the general allowlist, but decision, read, share, and submit endpoints have no maintainer/repository authorization. A judge admitted through a public invite can read another user's private PR analysis, share it, and approve it. `approved` becomes a successful GitHub status even for a malicious verdict. Human override can be intentional, but an invited guest should not acquire maintainer authority over every repository accessible to the App.

Confirmed with an authenticated FastAPI TestClient, temporary database, owner-created malicious PR run, and fake GitHub client: guest GET returned 200; guest approval returned 200; fake GitHub received `status(success)` and a comment. No real GitHub writes occurred.

Fix: separate owner/maintainer privileges from demo guest privileges. Restrict guests to their own runs and a designated public demo repository; authorize repository access and decisions server-side. Restrict sharing of private analysis too. Add negative authorization tests before publishing an invite.

### 2. [P1] Model-selected commands run as guest root and can compromise observation

References: `airlock/agent.py:95–99`, `airlock/sandbox.py:163–178`, `airlock/events.py:185–189`, `airlock/pipeline.py:83–85`.

The deterministic install runs as `node`, but the agent's exec tool does not pass `as_user`. Workspace therefore executes it as root. The prompt explicitly confirms this and merely asks the model to use `runuser` for reruns. If it directly runs package code, that code can kill the root watcher, alter its logs/resolver, or tamper with subsequent investigation. WatchTranslator additionally ignores root activity. Prompt injection can reach a privileged tool even without a VM escape.

Confirmed with a fake Workspace: `_tool('exec', ...)` passes no `as_user`. This is an observation-integrity weakness inside the guest; it is not evidence of host escape.

Fix: enforce `as_user='node'` for every model-selected exec. Keep privileged setup and evidence collection outside model control. Check guest image sudo/setuid capabilities before claiming the user boundary is secure.

### 3. [P1] Observation failures do not fail the analysis closed

References: `airlock/sandbox.py:144–161`, `airlock/guest/watch.py:97–110,243,336`, `airlock/pipeline.py:110–119,143–148`.

Watcher startup failure only emits an error and returns normally, so detonation/triage continue. Worse, the two `watch_ready` messages mean DNS and the main thread started; neither proves fanotify initialized or its marks succeeded. `watch_error` is not promoted to a pipeline failure. Install/test/unpack exit codes are also mostly ignored. Consequently an apparently quiet run can reflect failed coverage or failed execution, and the model is still allowed to return benign.

Confirmed with a fake sandbox whose shell always fails: `_start_watcher()` returned normally after recording only an error.

Fix: require positive readiness from every required observer, stop on observer failure, track install/test outcomes separately, and prohibit a clean behavioral verdict when required execution/coverage is incomplete. Preserve a distinct inconclusive result for analysis failures.

### 4. [P1] Long labels remove VM-name randomness; replacement can interfere with another run

References: `airlock/sandbox.py:90,107–110`.

The complete name, including its random suffix, is truncated to 60 characters. For a sufficiently long package/repository label, the suffix disappears. Two concurrent submissions then get the same name, and `Sandbox.create(... replace=True)` permits replacement of the existing named VM. The exact replacement behavior was not exercised on a real host, but uniqueness is already broken.

Confirmed without starting a VM: two Workspaces with the same 80-character label had identical 60-character names.

Fix: truncate the sanitized label first, then append an untruncated run identifier; avoid replacement for new per-run VMs.

### 5. [P1] “PROVEN” does not require the current run's canary or trusted provenance

References: `airlock/events.py:246–258`, `airlock/store.py` (`proven_exfil`), `airlock/web/static/app.js:242–244`, `airlock/sandbox.py:98–100,218–241`.

Sinkhole classification checks only for the public string `AIRLOCKCANARY`; it sets `proven=True` even when `this_run=False`. `Store.proven_exfil()` and self-tests ignore `this_run`. A hardcoded marker or another run's token therefore qualifies as proof. The UI also labels all Node tracer exfil events PROVEN, although `/tmp/airlock-trace.jsonl` is written by the package user and can be forged or truncated by it.

The fake /24 is selected randomly from 512 possibilities without reserving active allocations. Concurrent collisions can mix sinkhole records; the incorrect token check makes that more consequential.

Confirmed directly: a sinkhole body containing a different canary produced `proven=True, this_run=False`.

Fix: require the exact current token and host-side captured payload for the strongest proof label; treat guest tracer events as untrusted supporting telemetry. Reserve active subnets uniquely. State that payload capture proves an attempted transmission to Airlock, not successful delivery to an attacker or malicious intent by itself.

### 6. [P2] VM lifecycle reporting overstates cleanup guarantees

References: `airlock/sandbox.py:102–128`, `airlock/web/app.py:58–70`.

If setup raises after the inner sandbox context was entered but before Workspace returns, Python will not automatically call Workspace's `__aexit__`. Explicit cleanup of the already-entered inner context is missing. Separately, `vm_destroyed` is emitted in `finally` even if destruction raises. Confirmed with a fake failing destructor: the final event still said `vm_destroyed`.

Fix: clean up partial setup in an exception handler; emit successful destruction only after confirmation; record cleanup failures and reconcile abandoned VMs and running database rows at startup. A VM's maximum lifetime is useful but does not establish complete resource deletion after crashes.

### 7. [P2] Prompt guard coverage and evidence links are advisory, not enforced

References: `airlock/agent.py:108–145`, `airlock/pipeline.py:101,118–119`, `airlock/guard.py`.

The initial goal embeds the untrusted PR title, filenames, and event summaries directly into a user message without `_screen`. Later tool results use a small regex screen, and read-file exceptions also bypass it. The finish path accepts arbitrary evidence strings without checking cited event IDs exist or support the statement. “All untrusted text passes the guard” and “every claim links to the event that proves it” are therefore stronger than the implementation.

Fix: delimit and screen all untrusted inputs consistently; enforce allowed citation IDs structurally; distinguish observed events from the model's interpretation. A valid ID alone still does not prove the cited statement. Add adversarial tests beyond the readable README injection fixture.

### 8. [P2] npm spec validation allows shell operators in a root acquisition command

References: `airlock/web/app.py:28,195–198`, `airlock/pipeline.py:138–139`.

The version regex allows `|`, `<`, and `>` and the target is interpolated into a shell command unquoted. A string such as `left-pad@1|id|cat` passes validation and changes the shell pipeline, running the middle command as guest root during acquisition. Only acceptance/construction was checked; this command was not executed. Containment still places it inside the VM, but it bypasses the intended unprivileged detonation path and observation attribution.

Fix: shell-quote the entire npm spec or use an argv-based exec interface. Validate length and reject command syntax independently of version-range syntax.

### 9. [P2] Claimed merge gate requires repository configuration

References: `airlock/web/app.py:313–327`, `airlock/github.py:110–115`.

Airlock writes a status only after a human decision. It does not merge, install a required-status rule, or establish a pending status at submission. Without branch protection/rulesets requiring the appropriate App's `airlock` status, GitHub can allow merges without Airlock. Even with protection, a prior successful status on the same SHA can remain green during a rerun until a new decision posts.

Fix: document and demonstrate the required-status configuration; set pending when a new review begins; identify the expected App as the status source. Describe the current feature as posting a review decision unless the merge restriction is demonstrated.

## Other engineering follow-ups

- `airlock/github.py:85`: changed files stop at the first 100. Diff text is truncated at 200,000 characters without a completeness marker. Paginate and disclose truncation before claiming full PR review. The archive is fetched by head SHA, while diff/files are fetched by mutable PR number; pin/check the snapshot to avoid mismatches during a push.
- `roles.toml:4`: fallback is configured but never read by application code. No automatic model fallback exists.
- `airlock/web/app.py:177–188`: uploaded files have no deletion/retention path. The rolling guest cap can still admit about 3 GB/day of 20 MB uploads, before database/log growth. Host-side sinkhole logs and event queues also lack retention/backpressure. Add cleanup and host-side output/log limits.
- `Runner._run` has no overall analysis deadline. The 480-second VM lifetime does not cap repeated inference calls, retries, or how long a runner slot remains occupied. Add an end-to-end deadline and cancellation cleanup.
- `README.md:138–142`: “Run your own” is incomplete for an independent builder: `.env.example` is absent, deploy expects named 1Password references, default host/domain/owner and cloud-init SSH key are personal, and OAuth callback/App setup and branch rules need explicit steps. Document required substitutions and pinned versions. Cloud-init installs moving uv/microsandbox/mitmproxy versions, so it is rebuildable automation rather than a fully reproducible environment.

## Network assurance still requiring host verification

`Rule.allow_dns()` in the installed SDK allows UDP/TCP 53 to the sandbox gateway. Changing the guest's resolver to localhost does not itself prevent a package sending raw DNS directly to that gateway. Verify that arbitrary names sent there cannot reach an external recursive resolver and disclose data in DNS labels. This is a plausible bypass path, not a reproduced live exfiltration finding. Registry exceptions also need a test showing what data a request can send to them. Do not claim a universal “no canary leaves the host” guarantee on the strength of the fake-DNS happy path.

Test health loss after startup, truncated/forged tracer records, encoded/query/header-only canaries, observer failure, long labels under concurrency, and timeout/crash cleanup using controlled endpoints and fake credentials only. The existing fixtures are deliberately obvious and cannot establish those properties.

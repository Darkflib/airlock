## Remaining findings

### R1. [P1] Invited guests still receive all owner-created analysis

Reference: `airlock/web/app.py:170–175` (`readable`).

The current policy deliberately treats every owner's run as demo material, independently of `GUEST_REPOS`. That means a new private PR analysed by an owner immediately becomes readable to every invited guest, including evidence and captured payloads returned by the run API. Restricting guest PR submissions does not restrict these reads. The same filter governs SSE and the list.

Reproduced in a temporary database with an owner-created non-demo run carrying a private-source evidence string: guest GET returned **200**. Approval and sharing correctly returned **403**. This is safe only if the entire instance is intentionally dedicated to material every invitee may see; it does not isolate private owner work.

Recommendation: make demo visibility explicit per run, or allow guest reads of owner runs only when their repository is on the demo allowlist. Upload/npm runs need an explicit visibility decision too. Preserve owner access to all runs.

### R2. [P2] Coverage checks end before the investigation and ignore test failure

References: `airlock/pipeline.py:145–153`, `airlock/pipeline.py:185–191`.

The result of `npm test --if-present` is discarded. `coverage_gaps` receives only the install result. Both pipelines check observation health before `agent.run`, then apply that earlier snapshot after the agent finishes. A watcher that fails during investigation is therefore not detected by the final check. No gap is added when tests time out and part of the tested code never executes.

Reproduced with fake Workspace/agent/GitHub clients, without executing commands:

- Successful install, timed-out npm test, benign model verdict => **BENIGN**.
- Healthy observer before agent, observer marked dead during agent, benign model verdict => **BENIGN**; observation health checked only once.

Recommendation: retain and assess the test result (distinguish no test script from an interrupted test); recheck observation after the final agent tool execution and before accepting benign. Keep suspicious/malicious evidence, but disclose incomplete execution. A normal assertion failure alone need not mean maliciousness.

### R3. [P2] Malformed DNS can silently terminate the guest observation thread

References: `airlock/guest/watch.py:193–203,244–258,337–342`; `airlock/sandbox.py:218–228`.

Guest DNS parsing is still less defensive than the new host DnsGuard. A truncated question with a nonempty label can pass `qname` and reach `fake_answer`, which raises `IndexError`. The `dns_loop` has no per-packet exception boundary. Its daemon thread exits, while the main watcher sleeps indefinitely and no `watch_error` is logged. The health check checks the process and recorded errors, not worker-thread health or heartbeat.

Confirmed by evaluating only the trusted parser helpers on a truncated question: `qname` returned a nonempty name and `fake_answer` raised **IndexError: index out of range**. The resulting thread termination follows from the uncaught call in `dns_loop`; no packet was sent to the production service. Host DnsGuard still enforces the external DNS policy, so this finding is lost observation/availability, not a demonstrated renewed DNS exfiltration bypass.

Recommendation: reject malformed packets before response generation, catch/log per-packet parse errors, supervise worker threads, and require fresh per-observer health through the end of analysis. Add a malformed-query regression for the guest parser as well as the host guard.

### R4. [P2] Failed pending updates can leave an old green merge status

Reference: `airlock/web/app.py:140–158`.

`gate_pr` catches status-post failures and continues. Its comment assumes branch protection blocks without success, but the SHA may already have a successful `airlock` status from an earlier review. If pending updates fail, that success is not invalidated. Errors during archive/diff acquisition also occur before the metadata callback establishes pending. Concurrent same-SHA runs/decisions can overwrite one another because the status context has no latest-review ownership check.

Reproduced with a fake GitHub client initialized to `success` and configured to reject pending writes: both pending attempts failed, the new run completed **MALICIOUS** with no human decision, and the fake commit status remained **success**.

Recommendation: do not represent a new run as holding merge until pending is acknowledged; surface status-sync failure prominently and fail the review's gate state closed. Serialize or version decisions per repository/SHA, reject stale decisions, and document the limits when GitHub cannot be updated. Verify the required check's source App in branch rules. An unavailable GitHub API cannot be made to revoke a pre-existing success by local state alone.

### R5. [P2] Prompt screening and evidence validation remain advisory

References: `airlock/agent.py:103–113,140–147`.

The initial goal still directly includes PR title/filenames/event summaries, and read-file exception text bypasses `_screen`. Finish still accepts evidence strings without checking citation existence or support. Current wording that all untrusted text is screened or that citations necessarily point to real evidence is not established.

Recommendation: apply consistent untrusted-data boundaries and screening at every input path, validate cited IDs, and label the explanation as model interpretation. Retain regex screening as a limited heuristic rather than a prompt-injection guarantee.

### R6. [P2] The live homepage retains the old absolute claims

Reference: `airlock/web/static/index.html:24–25`.

The browser-loaded homepage still says fake credentials and **“no internet”**, then **“records everything it touches.”** Registry HTTPS is deliberately permitted and observation has documented gaps. This remains in local source as well as the visible live page, despite improved README/submission copy.

Recommendation: use the same accurate wording on the homepage: registry-only internet access and observed process/file/network activity. With the new merge-gate behavior, consistently distinguish automatic pending/error statuses from human-approved success/failure and comments; the short submission description still says nothing reaches GitHub before approval.

## Lower-priority items still open

- GitHub files remain limited to the first 100, diff to 200,000 characters without completeness markers, and mutable PR files/diff may not match the archived head SHA.
- Model fallback is still a role setting without runtime fallback logic.
- Uploaded-file/log retention, output/event backpressure and an end-to-end runner deadline remain absent.
- Independent deployment setup still depends on personal host/domain/SSH/1Password defaults and lacks a complete `.env.example`/OAuth/App setup path.
- Public repository, video, PDF slides, cover image, demo PR accessibility, and completed lablab submission remain checklist items to verify; no new presentation artifacts were reviewed here.

- A transient SyntaxError in the in-progress merge-status edit initially stopped collection. It was corrected during this review and is **not** a remaining finding.
- Current submission checks pass: title **38**, short description **253**, long description **1782** characters / **299** words.
- Independently read the latest recorded product regression, `product-20261104T014526Z`: **18/18** expected verdicts, **9** proven flags. This checks the recorded counts, not a new independent KVM run.
- Safe reproductions confirmed owner-run guest reads, test-timeout/late-observer gaps, malformed guest DNS parsing and stale green status on pending-write failure. Previously reported owner approval/sharing and wrong-token proof reproductions now fail as expected.
- Live homepage loads in the browser using the existing owner's session. No new run, decision, invite, share link or production status was created. Binary/deployed commit identity and live branch rules were not independently verified.

Most of the original security fixes are real. Prioritize R1 if this instance will inspect private material; then complete observation health and gate failure handling. Keep the original review as history rather than a current list of all-open issues.
